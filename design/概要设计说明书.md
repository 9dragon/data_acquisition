## 1. 设计概述

### 1.1 项目背景

本系统是工业数据采集项目的内部管理系统，用于管理数采实施过程中的项目、设备、进度、问题和文档。已完成需求规格说明书（V1.2）和前端原型设计。

### 1.2 系统目标

1. **项目全生命周期管理** - 从售前调研到验收的完整流程管理
2. **设备进度可视化** - 实时跟踪每台设备的数据采集进度
3. **问题快速响应** - 建立完整的问题跟踪和协同处理机制
4. **知识沉淀** - 项目文档的集中管理和分类体系

### 1.3 功能模块

| 模块 | 优先级 | 说明 |
|------|--------|------|
| 项目管理 | P0 | 项目列表、项目阶段、项目成员 |
| 设备管理 | P0 | 设备列表、设备类型、设备调研 |
| 工序车间 | P0 | 工序管理、车间管理、三级联动 |
| 权限管理 | P0 | 用户管理、角色权限、权限控制 |
| 进度管理 | P1 | 项目计划、进度填报、进度报告 |
| 任务管理 | P1 | 任务列表、任务依赖、任务资料 |
| 文档中心 | P1 | 文档管理、版本控制、标签管理 |
| 问题管理 | P2 | 问题列表、问题工作流、问题统计 |
| 工作台 | P2 | 待办事项、项目概览、进度预警 |

### 1.4 关键技术挑战

1. **复杂进度计算** - 双层推进方式（按任务/按设备），多层级进度聚合
2. **三级联动机制** - 项目 → 工序 → 设备类型
3. **任务依赖引擎** - FS/SS/FF/SF四种依赖关系
4. **细粒度权限控制** - RBAC + 数据级权限
5. **大文件上传** - 文档100MB、图片10MB、视频50MB

## 2. 技术选型

### 2.1 后端技术栈：Java Spring Boot

**选型理由**：
- 企业级应用首选，生态成熟，团队技能储备丰富
- 适合复杂业务逻辑和长期维护
- MyBatis-Plus提供强大的ORM支持
- Spring Security提供完善的权限控制
- 丰富的中间件支持（Redis、XXL-Job）

**核心组件**：
- 框架：Spring Boot 3.2
- ORM：MyBatis-Plus 3.5
- 数据库连接池：HikariCP
- 任务调度：XXL-Job（定时计算项目进度、逾期预警、报告生成）
- 文件存储：MinIO
- 缓存：Redis 7.0
- 权限：Spring Security + JWT
- 监控：Actuator + Prometheus

### 2.2 前端技术栈：Vue3

**选型理由**：
- 学习曲线平缓，上手容易
- Element Plus组件库完善，UI效果优秀
- Pinia状态管理简洁高效
- Vue Router 4路由功能强大
- AI代码生成友好，开发效率高

**核心组件**：
- 框架：Vue 3.4 + TypeScript 5.3
- 状态管理：Pinia 2.1（跨组件状态管理，如用户信息、项目缓存、权限数据）
- UI组件：Element Plus 2.5
- 路由：Vue Router 4.2
- 构建：Vite 5.0
- 图表：ECharts 5.4
- 工具库：VueUse 10.7

### 2.3 数据库：MySQL 8.0

**选型理由**：
- 国内使用最广泛（>90%市场占有率）
- 运维成熟，人才储备丰富
- 云服务支持最好（阿里云RDS、腾讯云等）
- JSON类型足够支持半结构化数据
- 全文搜索通过ngram插件支持中文

**配置要求**：
- 字符集：utf8mb4（支持emoji和完整Unicode）
- 排序规则：utf8mb4_unicode_ci
- 存储引擎：InnoDB（支持事务和外键）

## 4. 核心模块设计

### 4.1 权限控制模块

#### 4.1.1 权限模型（RBAC）

```
用户 (User)
  │
  ├────> 角色 (Role)
  │        │
  │        └────> 权限 (Permission)
  │                 │
  │                 └────> 资源:操作 (Resource:Action)
  │
  └────> 数据权限
           ├────> 项目级：项目经理拥有项目下所有数据权限
           ├────> 设备级：设备负责人仅拥有负责设备的数据权限
           └────> 只读：普通用户仅有查看权限
```

#### 4.1.2 权限验证机制

1. **功能权限验证**：基于RBAC模型，验证用户是否拥有执行某操作的权限
2. **数据权限过滤**：根据用户角色自动过滤可访问的数据范围
3. **接口级拦截**：通过拦截器统一验证Token和权限
4. **前端路由守卫**：前端路由层进行权限预判断，无权限直接拦截

### 4.2 进度计算模块

#### 4.2.1 进度计算层级

```
任务进度 → 设备进度 → 阶段进度 → 项目进度
```

#### 4.2.2 两种推进模式

**按任务推进**：
```
阶段进度 = 已完成任务数 / 总任务数 × 100%
```

**按设备推进**：
```
无任务级填报：
  阶段进度 = 已完成设备数 / 总设备数 × 100%

有任务级填报：
  设备进度 = Σ(各设备任务完成率) / 设备总数
  阶段进度 = Σ(各设备进度) / 设备总数
```

#### 4.2.3 计算触发时机

1. **实时计算**：进度填报时立即计算并保存
2. **定时计算**：每日凌晨通过XXL-Job定时重算所有项目进度
3. **缓存优化**：热点项目进度数据缓存到Redis

### 4.3 工序联动模块

#### 4.3.1 三级联动机制

```
项目选择 → 工序筛选 → 设备类型筛选
    │           │              │
    └──────更新──────────────────┘
```

#### 4.3.2 联动规则

1. 选择项目后，工序下拉框只显示该项目的工序
2. 切换项目时，已选工序自动清空
3. 选择工序后，设备类型只显示该工序下的类型
4. 设备类型的工序可以不选（通用类型）

### 4.4 任务依赖模块

#### 4.4.1 依赖类型

```
FS (Finish-to-Start): 前置任务完成后，后续任务才能开始
SS (Start-to-Start): 前置任务开始后，后续任务才能开始
FF (Finish-to-Finish): 前置任务完成后，后续任务才能完成
SF (Start-to-Finish): 后续任务开始后，前置任务才能完成
```

#### 4.4.2 依赖检查机制

1. **前置检查**：任务开始前检查所有前置任务是否完成
2. **循环检测**：添加依赖时检测是否存在循环依赖
3. **级联影响**：任务延期时自动计算受影响的后续任务
4. **可视化展示**：甘特图展示任务依赖关系

### 4.5 大文件上传模块

#### 4.5.1 文件分类与限制

```
文档文件: 最大100MB（Word、Excel、PPT、PDF）
图片文件: 最大10MB（JPG、PNG、GIF）
视频文件: 最大50MB（MP4、AVI、MOV）
CAD文件: 最大50MB（DWG、DXF）
```

#### 4.5.2 分片上传方案

1. **分片大小**：5MB每片
2. **上传流程**：初始化 → 上传分片 → 合并分片 → 完成
3. **断点续传**：记录已上传分片，支持续传
4. **进度反馈**：实时返回上传进度
5. **同步处理**：分片上传完成后同步合并，用户等待处理完成

#### 4.5.3 存储策略

1. **本地存储**：开发环境和测试环境使用本地磁盘
2. **MinIO存储**：生产环境使用MinIO对象存储
3. **CDN加速**：静态资源通过CDN加速访问

## 5. 接口设计规范

### 5.1 RESTful API规范

#### 5.1.1 基础规范

- **基础路径**：`/api/v1`
- **认证方式**：Bearer JWT
- **请求格式**：`application/json`
- **响应格式**：`application/json`
- **字符编码**：`UTF-8`

#### 5.1.2 URL命名规范

```
资源命名: 小写、复数、驼峰分隔
示例:
  /api/v1/projects
  /api/v1/device-types
  /api/v1/project-stage-configs

关联资源:
  /api/v1/projects/{projectId}/stages
  /api/v1/projects/{projectId}/members
  /api/v1/devices/{deviceId}/progress
```

#### 5.1.3 HTTP方法规范

```
GET    - 查询资源（幂等）
POST   - 创建资源
PUT    - 全量更新资源（幂等）
PATCH  - 部分更新资源（幂等）
DELETE - 删除资源（幂等）
```

### 5.2 统一响应格式

#### 5.2.1 成功响应

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { /* 业务数据 */ },
  "timestamp": "2026-03-20T10:30:00Z"
}
```

#### 5.2.2 分页响应

```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "list": [],
    "total": 100,
    "page": 1,
    "pageSize": 10,
    "totalPages": 10
  },
  "timestamp": "2026-03-20T10:30:00Z"
}
```

#### 5.2.3 错误响应

```json
{
  "code": 1001,
  "message": "用户名或密码错误",
  "details": {},
  "timestamp": "2026-03-20T10:30:00Z"
}
```

### 5.3 错误码规范

| 错误码范围 | 说明 |
|-----------|------|
| 200 | 成功 |
| 1001-1999 | 认证授权错误 |
| 2001-2999 | 业务逻辑错误 |
| 3001-3999 | 参数验证错误 |
| 4001-4999 | 资源不存在错误 |
| 5001-5999 | 服务器内部错误 |

## 6. 安全设计

### 6.1 认证设计

#### 6.1.1 JWT认证流程

```
1. 用户登录 → 验证用户名密码
2. 生成JWT Token（包含用户ID、角色、过期时间）
3. 返回Token给客户端
4. 客户端每次请求携带Token
5. 服务端验证Token有效性
6. 提取用户信息到上下文
```

#### 6.1.2 Token策略

- **Access Token**：2小时过期
- **Refresh Token**：7天过期
- **Token刷新**：Access Token过期前使用Refresh Token刷新

### 6.2 授权设计

#### 6.2.1 功能权限（RBAC）

```
用户 → 角色 → 权限 → 资源:操作
```

#### 6.2.2 数据权限

```
项目经理: 项目下所有数据的完全控制权
设备负责人: 仅负责设备的操作权限
普通用户: 仅查看权限
```

### 6.3 数据安全

#### 6.3.1 密码安全

- **加密算法**：BCrypt
- **加密强度**：10轮
- **密码策略**：8-20位，必须包含字母和数字

#### 6.3.2 传输加密

- **传输加密**：HTTPS/TLS 1.3
- **存储加密**：敏感字段使用AES-256加密

### 6.4 审计日志

#### 6.4.1 日志记录内容

```
- 用户登录/登出
- 资源的创建/修改/删除
- 权限变更
- 数据导出
- 敏感操作
```

#### 6.4.2 日志保留

```
保留时间: ≥180天
日志级别: INFO/WARN/ERROR
```

### 7.4 Docker Compose部署支持

系统设计遵循容器化优先原则，所有组件支持通过Docker Compose进行一体化部署：

**部署能力**：
- 支持开发/测试/演示环境的一键启动
- 支持生产环境的小规模单机部署
- 所有服务组件（前端、后端、MySQL、Redis、MinIO）均提供Docker镜像

**设计要求**：
- 后端服务支持容器化部署，配置外部化（环境变量/配置文件）
- 前端静态资源支持Nginx容器化部署
- 中间件依赖使用官方镜像，通过Docker Compose编排
- 数据持久化通过Volume挂载实现

**部署优势**：
- 降低部署复杂度，减少环境配置差异
- 快速搭建开发/测试环境
- 支持水平扩展（通过调整容器副本数）
